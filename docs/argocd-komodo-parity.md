## Scoring method

Each of the 309 matrix rows carries a Komodo status (`have`=1.0, `partial`=0.5, `missing`=0.0, `na`=excluded) and a `weight` (1–5, importance-weighted) and a `tier` (0–3, the investment tier at which Komodo would fully close that row's gap). Weighted parity at cumulative tier *N* is:

```
covered(N) = Σ [ have→weight ] + Σ [ partial→weight×0.5, +weight×0.5 more if row.tier ≤ N ]
                                + Σ [ missing→weight if row.tier ≤ N, else 0 ]
parity(N)  = covered(N) / Σ weight   (na rows excluded from both sides)
```

This is monotonic and reaches exactly 100% at N=3 by construction (every row's tier is ≤3), so tier-3 "100%" is a tautology of the scoring method, not a claim that full parity is achievable — it just means every gap in the matrix has *some* nameable path to closure. The real signal is in the tier-0/1/2 numbers, which are not tautological.

Raw counts (all 300 non-`na` rows, 9 `na` rows excluded): **28 have** (9.3%), **61 partial** (20.3%), **211 missing** (70.3%). Total weight across non-`na` rows: 716. Core-value subset (weight ≥4): 60 non-`na` rows, total weight 262.

Method limitations, stated honestly: (1) "tier" was assigned by the research agents per-row against the effort doc's tier definitions, not independently re-derived here — a systematic tier-inflation or -deflation bias in the source matrix would shift these numbers uniformly. (2) Weight is a 1–5 importance-judgment call per row, not derived from usage telemetry of either product. (3) 151 of 309 rows (49%) are marked `UNVERIFIED` — no adversarial re-check ran against them — so their `komodo_status`/`gap` text is single-pass-researcher-only; the 149 `CONFIRMED` + 8 corrected rows are higher-confidence. (4) Partial credit at 0.5 is a modeling choice — some `partial` rows (e.g. Komodo's RBAC engine, weight 4, genuinely close to Argo's Casbin model) arguably deserve more than 0.5; others (e.g. a single `links: Vec<String>` field standing in for Argo's structured `spec.info`) arguably deserve less. (5) The matrix conflates "Argo CD feature Komodo lacks for Kubernetes" with "Argo CD feature Komodo lacks for its own Docker/Swarm resources" in the `have`/`partial` rows — read the Mechanism/Gap cell, not just the status symbol, before citing a number.

## Five things Argo CD has that Komodo structurally cannot get cheaply

**The reconcile loop.** Argo CD's application controller runs a continuous watch/informer loop against the live Kubernetes API, correcting drift the instant it's observed. Komodo's closest analog, `spawn_resource_refresh_loop` (`bin/core/src/resource/refresh.rs:42-63`), is a plain timer (`resource_poll_interval`, default 1 hour) that calls `refresh_syncs()` — which only calls `RefreshResourceSyncPending` (recompute a diff preview) and **never** calls `RunSync` (`refresh.rs:137-162`, read directly: no call site anywhere applies the correction automatically). One layer down, Periphery has no watch/informer mechanism at all: `PollStatus` (`bin/periphery/src/api/poll.rs:16-46`) is a plain request/response RPC that Core re-issues on a fixed 15s timer (`bin/core/src/monitor/mod.rs:53-60`) — Periphery answers fresh each call, it does not push state changes. Building a real reconcile loop means replacing this entire poll-and-preview architecture with a watch-based controller reading live object state continuously, which is tier-3 work by the matrix's own count (weight 5, `core-sync-engine-reconcile-loop`) — not a shellout tweak layered onto the existing timer.

**The live-state diff/health model.** `get_diff` (`bin/core/src/sync/mod.rs:96-101 + bin/core/src/sync/resources.rs:37-41`) is `original.partial_diff(update)` — a field-by-field diff of two Rust structs Komodo itself owns (the DB-stored `Config` and the incoming TOML `PartialConfig`). It has never, in any code path, compared against a live runtime object (no `docker inspect` diff, let alone a `kubectl get -o json` diff). `StackState`/`DeploymentState` (`client/core/rs/src/entities/stack.rs:216-236`) are a 5-value Docker-lifecycle enum (Running/Paused/Stopped/Unhealthy/Down) computed from `docker inspect`, with zero per-Kubernetes-kind readiness semantics (Deployment rollout status, Ingress LB address, Job completion, PVC bound) and no customization hook. Building Argo's model needs both a live-object read path (which planning-e3y.6's one-shot `kubectl diff` execution-log approach only weakly substitutes for) and a per-GVK health-check table Argo built via Lua scripts — neither exists in any partial form.

**The Application abstraction.** Komodo has 11 fixed resource types applied in a hardcoded compile-time order (`bin/core/src/api/execute/sync.rs:318-397`: Variables/UserGroups → Server/Alerter/Action → Swarm/Builder/Repo → Build/Stack/Sync/Deployment → Procedure). There is no single object that wraps an arbitrary, heterogeneous set of typed Kubernetes objects with owner-references, per-object sync-wave ordering, and worst-child health rollup the way an Argo `Application` does. The closest thing — a Stack's `file_contents` — is opaque text handed to `docker compose up`; there is no multi-object manifest model at all (confirmed by the 5/5-weight `sources-clusters-directory-plain-manifests` and `sources-clusters-multiple-sources` rows, both fully `missing`). This is a data-model gap, not an execution-model gap, and it compounds with the reconcile-loop and health-model gaps above: even a hypothetical Cluster resource applying raw manifests via `kubectl apply -f` would not have anywhere to hang wave/health/hook metadata per object inside that manifest set.

**Multi-cluster fan-out.** Every Stack/Deployment binds to exactly one Server XOR one Swarm (`swarm_id`/`server_id` precedence, `client/core/rs/src/entities/stack.rs:303-327`), because one Periphery process holds exactly one `bollard::Docker` connection to exactly one host (`bin/periphery/src/docker/mod.rs:29-35`, `DockerClient::connect()`). There is no ApplicationSet-equivalent generator engine anywhere — every one of the 9 Argo generator types (List/Cluster/Git-directory/Git-file/SCM-Provider/PullRequest/ClusterDecisionResource/Matrix/Merge) scores `missing` in this matrix, 31 of 42 rows in the ApplicationSets & Projects domain. Fanning one deploy out across N clusters needs a templating/generator subsystem that renders N resource configs from a parameter source — Komodo's variable interpolation (`lib/interpolate/src/lib.rs:9-134`) is single-value `[[var]]` string substitution into one resource's own config, not a fan-out template evaluated once per matched cluster/directory/PR.

**Per-user cluster identity.** `PeripheryClient::request` (`bin/core/src/periphery/mod.rs:84-153`) serializes only `{type, params}` over the wire — no user/operator field is ever included. Every command Periphery executes (docker CLI, git, and any future kubectl) runs as the Periphery process's own OS identity (`lib/command/src/lib.rs:128-161,182-203`, plain `tokio::process::Command`, no uid/gid switch, no impersonation). The Noise-protocol handshake (`lib/transport/src/auth.rs:45-134`) authenticates the whole Core process to the whole Periphery process once per connection — it is a service-to-service trust relationship, not a per-Komodo-user credential. A future Cluster resource holding one kubeconfig means every Komodo user who can Deploy against that Cluster hits the Kubernetes API as the exact same identity, with the exact same RBAC grants, unless Komodo builds a SelfSubjectAccessReview-aware impersonation layer (`--as` header forwarding) — architecturally a brand-new capability, not a config flag, because the current transport was built to authenticate hosts, not humans.

**Recommendation: reaffirm the prior doc's call — do not chase tier 2.** The new evidence sharpens rather than overturns it. Shipping every currently-specced Cluster resource ticket (tier 1, ~6-10 weeks solo per the effort doc) buys 11.4 points of core-value weighted parity (31.9% → 43.3%) — a real, shippable "kubectl bridge for ad-hoc ops and light GitOps via `on_pull` hooks," consistent with what tier 0 already provides today (`docs/komodo-kubernetes-support-effort.md`'s tier-0 zero-code path). Getting the next 44.9 points (43.3% → 88.2%) requires standing up six subsystems that do not exist in any partial form — a templating engine, a live-object diff engine, a per-GVK health-check table, a continuous reconcile loop, an RBAC policy language, and a generator/multi-tenancy engine — each independently sized at 3-6wk-to-3mo in this matrix, several explicitly tier-3 (6mo+, e.g. the reconcile loop and controller sharding). That is Argo CD's (and Flux's, and Rancher's) entire reason for existing; Komodo racing to rebuild it from scratch, on top of a Core↔Periphery↔one-host architecture that was never designed for a watch-based live-object model, is not a good trade against Komodo's actual differentiated position: Docker/Swarm host management, image builds, host terminals/stats, and a unified audit/notification/RBAC layer that Argo CD structurally does not have (see "What Komodo has that Argo CD does not" above) and would not gain by building Kubernetes support. Ship tier 1, point users who need real Kubernetes GitOps reconciliation at Argo CD/Flux, and let Komodo own the hosts underneath (including the hosts those tools run on).
